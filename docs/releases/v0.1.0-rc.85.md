# v0.1.0-rc.85

## What you will notice

- **Vector filters are on by default** (ADR-0059). `VEC.CREATE ... FIELD
  <name> TAG|NUMERIC` declares fields read from each vector's `META`, and
  `VEC.SEARCH ... FILTER "<expr>"` returns only the vectors that match, in
  RediSearch's query syntax for tags and numbers. In rc.84 they were served
  only with `vec-filters on`. To keep them refused, set `vec-filters off` in
  the inventory. See `docs/vectors.md`, "Filtering by metadata".
- **`VEC.SEARCH` refuses an option it does not know.** This came in rc.84,
  whose release page did not say so. Releases before rc.84 passed over an
  unknown option, so a `FILTER` sent to one was answered as if there were no
  filter. A client that sends an option Flint does not serve now gets
  `ERR unknown VEC.SEARCH option (want EF, RERANK or FILTER)`.
- **A tenant can no longer crash the vector co-processor** with a row it
  writes itself (BUG-0265). The co-processor keeps its durable rows in the
  tenant's namespace, under keys that start with `\x00vec\x00`. In rc.84, a
  row of the wrong length that a tenant wrote into a `QUANT bin` set crashed
  the co-processor at its next restart, for every tenant. Its rebuild now
  checks each row, leaves out any that does not fit its set, and says how
  many it left out.
- **A tenant's `FLUSHALL` or `FLUSHDB` now empties its vector sets too**
  (BUG-0268). In rc.84 a vector set went on answering from the co-processor's
  memory after a flush had deleted its rows, and a `VEC.SET` into it after
  the flush was acknowledged and then lost at the co-processor's next
  restart. If a co-processor cannot be told of a flush, the flush still
  happens and the reply is an error asking you to send it again. While a
  co-processor is down, every flush through the proxy answers that error.
- **Optional: the co-processor's rows can be closed to tenants**
  (`reserve-coproc-rows on`, off by default, BUG-0265). With it on, a data
  node refuses a tenant's own write to a `\x00vec\x00` key, from any command
  or script, and the co-processor still writes its rows. Turn it on only once
  every proxy in the fleet runs rc.85: the proxy is what marks the
  co-processor's connections, and an rc.84 proxy does not. The next release
  turns it on by default.
- **`flintctl verify` checks every declared co-processor** (BUG-0266). A new
  `== co-processors` section asks each `coproc` line in the inventory for
  `FLINTINFO`, and fails, naming it, if one does not answer: `FAIL
  co-processor up VEC. <addr> does not answer (...)`. A fleet whose
  co-processor was down passed verify on rc.84 and fails it on rc.85. That
  includes the verify that `bootstrap`, `upgrade`, `expand` and the other
  topology commands end with. Those still retry for 30 seconds, so a seat
  that is still starting is waited for.

## What you must do

Nothing, to upgrade. Check that your clients send only the `VEC.SEARCH`
options in `docs/vectors.md` (`EF`, `RERANK`, `FILTER`): anything else is now
an error.

## Rolling back

Rolling back to rc.84 is supported:
- **Filters stay served.** This release's `flintctl` passes rc.84's opt-in.
  Do not roll back below rc.84 once a tenant uses `FILTER`: a co-processor
  from before rc.84 answers it as if there were no filter.
- **Set `reserve-coproc-rows off` first,** if you turned it on. A data node
  from before this release does not know the flag, and refuses to start with
  it.
- **Verify's co-processor section** is simply absent from an older
  `flintctl`.
