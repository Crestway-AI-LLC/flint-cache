## What you will notice

- **RediSearch's `FT.*` vector commands, off by default** (ADR-0060). These
  are what redisvl, langchain-redis and LlamaIndex's Redis store send. With
  `coproc-ft on` in the inventory, each `VEC.` co-processor serves:
  - `FT.CREATE` over your own HASH or JSON keys;
  - `FT.SEARCH` with `=>[KNN ...]`, ADR-0059's filter, and vector ranges,
    `@field:[VECTOR_RANGE <radius> $vector]` (ADR-0061), which the
    frameworks' semantic caches send;
  - `FT.INFO`, `FT._LIST`, `FT.DROPINDEX` and aliases.

  A write under an index's prefix goes through the co-processor, so the
  index never misses it. A write under that prefix that does not come that
  way is refused with `-INDEXED`. `MODULE LIST` answers `search`, so the
  clients find it. What is served, and what is refused by name, is in
  `docs/command-support.md`. Without `coproc-ft on`, `FT.CREATE` is refused.
- **A co-processor answers sooner after a restart** (ADR-0017). The first
  command for a namespace it has not loaded yet waits up to 100 ms for that
  namespace's rebuild. If the rebuild finishes in that time, the command is
  answered instead of `-LOADING`. A larger namespace still answers
  `-LOADING` until it is loaded.
- **The co-processor's rows are closed to tenants by default** (BUG-0265).
  Every data seat now runs with `reserve-coproc-rows`: a tenant's own write
  to a `\x00vec\x00` key is refused, from any command or script, and the
  co-processor still writes its rows. In rc.85 this was opt-in. To let
  tenants write those keys, set `reserve-coproc-rows off`.

## What you must do

- **Upgrading from rc.85:** nothing. Its proxies already mark the
  co-processor's connections, which the closed rows need.
- **Upgrading from rc.84 or earlier:** set `reserve-coproc-rows off` until
  every proxy runs this release. An older proxy does not mark the
  co-processor's connections, so a data seat would refuse the co-processor's
  own writes.
- **Before `coproc-ft on`:** every seat must run this release. A seat of an
  earlier release does not refuse a write around the co-processor.

## Rolling back

- **To rc.85, nothing to change for the closed rows.** rc.85 knows
  `reserve-coproc-rows`, and this release's `flintctl` keeps passing it.
  Below rc.85, set `reserve-coproc-rows off` first: a data node from before
  rc.85 does not know the flag, and refuses to start with it.
- **If you turned on `coproc-ft`, drop every FT index before rolling back.**
  rc.85 knows neither the indexes' prefixes nor their routing, so a tenant's
  writes would reach the pairs and the indexes would miss them.
