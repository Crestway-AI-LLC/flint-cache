## What you will notice

- **A backup schedule that stops working can be alerted on** (ADR-0011's
  D8 amendment). The schedule used to record its failures, and the age of
  the newest set it had proven restorable, only in a status file nothing
  read. Name a status port in the inventory, `backup-listen <host:port>`, and
  `flint-backup schedule` answers `PING` and `FLINTINFO` on it, read-only.
  `restorable_overdue` is `1` when the newest set the strongest check proved
  (a rehearsal, else a verify, else the backup completing) is older than
  `restorable_bound_s`, which the seat computes from its own cadence.
  `flint-exporter --backup <host:port>` publishes it as
  `flint_backup_restorable_overdue`, the field to alert on. A job's failure
  streak is journaled once at its start, `BackupJobFailed` with the error,
  and once at its end, `BackupJobRecovered`.

- **A control-plane seat whose store cannot be written ends itself**
  (BUG-0282). On a three-seat control plane, a seat that was leader when a
  write to its own store failed (a full or read-only volume) went on
  answering as the leader, and could keep renewing the write lease of a
  master the real leader had fenced. It now exits, status 70, saying why,
  and the supervisor starts it again from what its store holds.

- **A write the storage engine refuses is answered as an error, whatever
  the command** (BUG-0283). Only a plain `SET key value` used to report it.
  `HSET`, `APPEND`, `SET … EX`, `INCR` and every other write reached the
  engine through a call that dropped RocksDB's error, and a client was told
  `:1` or `OK` for a write the engine had refused, on a full or failing
  volume. They now answer `ERR write failed: <RocksDB's message>`. A slot
  move whose destination's engine refuses an imported row now rolls back,
  and the source keeps the slot, where the rows had been lost. A command
  that writes several rows can still keep the rows written before the
  refused one.

- **A key the storage engine cannot read answers an error, and nothing is
  written over it** (BUG-0284). A key in a block RocksDB could not read
  (its checksum failed: a bad sector, a bit flipped at rest) answered as
  missing: `GET` returned nil, `DBSIZE` and the other scans stopped short,
  `INCR` stored 1 over the value, `SET NX` stored over it, and the GC
  deleted the fields of a hash whose meta row it could not read, and
  those writes replicate like any other. Such a key now answers `ERR read failed:
  Corruption: …`, a command, transaction, script or queued batch that met
  one writes nothing, the GC leaves the rows alone, and a slot move whose
  source cannot read the slot is refused. The server logs it, once every
  10 s at most. The bad block stays bad: the node's copy needs replacing
  from a healthy one.

- **A seat whose storage engine stops taking writes ends itself**
  (BUG-0285). Once a WAL append or sync fails (a full volume, an I/O
  error), RocksDB refuses every write until the database is opened again.
  The seat used to stay master, answering reads and refusing every write,
  until someone restarted it, with `disk_verdict:ok` once space was back. It
  now exits with status 70, logging `the storage engine refused 3 WAL syncs
  in a row`, within about two seconds of the first refused write; its
  supervisor starts it again, and opening the database recovers every
  acknowledged write.

- **A seat that cannot read its role row does not start** (BUG-0286). A
  seat whose role row sat in a block RocksDB could not read took it for no
  role: it started again at epoch (0,1) with the role its flags named, and
  its fence then let a stale `FLINTPROMOTE` through. It now refuses to
  start, naming the row and BUG-0286, and a role command that cannot read
  the row answers `ERR manifest: the storage engine read failed: …` and
  changes nothing. Replace such a seat's store from a healthy copy. `ERR
  manifest:` replies now read as text (`fenced: the stored epoch is …`)
  rather than Rust's debug form.

## What you must do

- **Upgrading from rc.87:** nothing. To alert on an overdue backup, add
  `backup-listen` with the backup host's address (not a wildcard: it is
  dialled), and point your exporter at it.

## Rolling back

- **To rc.87:** remove any `backup-listen` line from the inventory first.
  An rc.87 `flintctl` refuses a key it does not know.
