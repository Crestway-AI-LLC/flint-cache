# BUG-0111 — omitting one inventory line gave a plaintext mesh the security page said could not exist (FIXED 2026-09-06)

**Status: FIXED 2026-09-06**, and held by `require_tls_unless_disposable` in
`flintctl` plus a unit test on its pure predicate. Found 2026-09-06 while
finishing the `docs/security.md` audit that produced BUG-0109 · Severity:
medium — no deployed fleet was affected, and the claim was stated as an
impossibility rather than a recommendation, which is the kind a reader stops
checking.

## Symptom

`docs/security.md` opened with:

> **The internal mesh is mutually authenticated TLS, everywhere.** … There is
> no plaintext internal hop to turn off, and no "trusted network" assumption.

There was one, and turning it off took removing a line rather than adding
one:

```rust
#[derive(Debug, Clone, Default)]
struct Inventory {
    tls: bool,          // <- false unless the inventory says `tls on`
```

```rust
fn internal_args(inv: &Inventory) -> Vec<String> {
    if !inv.tls {
        return Vec::new();   // no --internal-ca, --internal-cert, --internal-key
    }
```

So a hand-written inventory without `tls on` bootstraps a fleet whose seats
were never given a CA, a certificate or a key, and every internal hop —
replication, migration, cutover, proxy↔backend, proxy↔control-plane, the Raft
RPCs between control-plane seats — runs in plaintext with no peer
authentication anywhere.

## Why no deployed fleet was affected

`packaging/aws/render-inventory.sh` emits `tls on` and `client-tls on`
unconditionally, under a comment that says the security posture is **not
parameterized**. Every production inventory is generated by it.

That is exactly the shape `require_release_or_disposable` already argues
against, one guarantee over:

> Enforced HERE rather than in the script that generates the inventory,
> because a guard you can step around by invoking the tool directly is a
> convention, not a guard.

The TLS posture was a convention. It held because nobody hand-wrote a
production inventory, not because anything stopped them.

## Fix

`flintctl bootstrap` refuses an inventory with neither `tls on` nor
`disposable on`, and says what to add. Two scoping decisions:

- **`bootstrap` only.** It is where the posture is chosen and where the CA is
  minted, so it is the last moment the choice is free. Gating every mutating
  verb would strand a fleet that predates the guard — `stop` is mutating too,
  and refusing to stop a plaintext cluster helps nobody.
- **`disposable on` is exempt**, meaning the same thing it means for the
  release guard: a cluster that exists for one run and is deleted after. All
  88 drill inventories in `tools/` are exactly that shape, declaring
  `disposable on` and no TLS. A guard that broke every drill would be turned
  off rather than satisfied.

## Verification

The decision is a pure predicate, `bootstrap_would_be_plaintext`, so all four
combinations are asserted without a fleet — including the one that matters
most, `disposable on` with no TLS staying allowed — plus five non-bootstrap
verbs staying ungated.

All three live paths were also run against a **release-tagged build**, which
was necessary: `FLINT_RELEASE_TAG` is baked in at compile time, so a first
attempt with the variable set at runtime hit the release guard instead and
proved nothing about this one.

| inventory | result |
|---|---|
| non-disposable, no `tls on` | refused, with the message above |
| `disposable on`, no `tls on` | bootstraps — `tls off` |
| non-disposable, `tls on` | bootstraps — mints the CA, keys 0600 |
