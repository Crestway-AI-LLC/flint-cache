# Release signing

Every published release is signed with [minisign](https://jedisct1.github.io/minisign/).
The public key is [`minisign.pub`](../minisign.pub) in the repository root and
is also attached to each release.

**Key ID `6A8EB70496EA74A1`** — in use since v0.1.0-rc.28. Quote this when
confirming the key through a second channel; a key fetched from the same place
as the artifact proves nothing about the artifact.

## Verifying a release

```sh
minisign -Vm flint-<version>-linux-x86_64.tar.gz -P "$(tail -1 minisign.pub)"
```

`Signature and comment signature verified` means the bytes came from the Flint
release pipeline. Anything else means they did not — stop.

The manifest is signed too:

```sh
minisign -Vm manifest.json -P "$(tail -1 minisign.pub)"
```

**Pin the key once, out of band**, and check every future release against your
pinned copy. A key you fetch from the same place as the artifact proves
nothing about the artifact.

### Why not just the checksum

`manifest.json` carries a sha256, and it is worth checking — but it only
proves the tarball matches *that manifest*. Whoever can replace the tarball on
a mirror can replace the manifest beside it. The signature is tied to a
private key that never leaves the release pipeline, so it survives the artifact
travelling through a CDN, a corporate mirror, or a USB stick into an
air-gapped site. That is the difference between "not corrupted" and "from us".

## Creating the key (once)

The private key is a **credential**: it is generated by a human, stored only
as a GitHub Actions secret, and never committed.

```sh
minisign -G -W -p minisign.pub -s minisign.key
```

`-W` produces a key with no password, which is what lets CI sign unattended.
That makes the file itself the whole secret — treat it accordingly.

Then:

1. Commit `minisign.pub` to the repository root.
2. Store the **contents of `minisign.key`** as the repository secret
   `MINISIGN_SECRET_KEY` (Settings → Secrets and variables → Actions).
   Paste the whole file, both lines.
3. Keep an offline copy of `minisign.key` somewhere durable. Losing it means
   rotating the public key, and every user who pinned the old one has to be
   told — out of band, which is slow and erodes exactly the trust the key
   exists to create.
4. Delete the working copy: `rm minisign.key`.

The release workflow **fails closed**: no `minisign.pub`, or no
`MINISIGN_SECRET_KEY`, and the publish step stops rather than shipping
unsigned artifacts that look like every other release.

It also verifies each signature against the *committed* `minisign.pub` before
publishing. If the CI secret ever drifts from the published key — a rotation
done halfway, a secret pasted from the wrong keypair — the release fails
instead of shipping signatures nobody can check.

## Rotating

1. Generate a new keypair.
2. Publish the new `minisign.pub` and announce it, signed with the OLD key, so
   the rotation itself is verifiable by anyone already pinned.
3. Update `MINISIGN_SECRET_KEY`.
4. Keep the old public key in the repository (renamed, e.g.
   `minisign.pub.2026`) so historical releases stay verifiable.

Rotate on compromise, or on a schedule if your buyers require one. Do not
rotate casually: every pinned copy in the field has to be updated by hand.
